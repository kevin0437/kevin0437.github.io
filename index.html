Case study

From ticket to merged pull request, with a person only where judgement is needed

An automated workflow that takes tickets from a GitHub Project board, has Claude agents build and review them, and merges what passes its rules. People see one page: what needs them.

The problem

More well-specified tickets than hands, and review already the bottleneck

Coding agents could write the code. The question was how to let them work through a board unattended without giving up control: who decides what gets built, what gets posted on GitHub in the team's name, and what gets merged.

What it does

One ticket's track

Every ticket moves along the same stages. Each stage belongs to an agent, a rule or a person, and the person's stages are kept as few as the risk allows.

  1. Person

    Label the ticket

    One label on a board card hands it over.

  2. Agent

    Build

    Own branch and workspace; runs the tests, reviews its diff, opens a PR. Asks instead of guessing.

  3. Rule

    CI and CI reviewer

    Medium findings and worse go back to the builder before any costlier review.

  4. Agent

    Second review

    Against the acceptance criteria, the repo's rules and its high-risk paths.

  5. Person

    Needs you

    Drafts on teammates' PRs, questions, anything a rule would not decide.

  6. Rule

    Auto-merge policy

    A pass is approved and queued only if every rule holds; if not, it comes back with the reason.

  7. GitHub

    Merged

    Through the merge queue. A builder PR the queue drops is retried once or sent back with why.

Agent Rule Person On a fresh demo repository: label to passing PR with a saved review in about 5.5 minutes, $0.90 at API prices.

Decisions worth explaining

Where control stays, and why

A person decides what goes out on other people's work

A review of a teammate's PR is a draft until a person posts it. Only reviews of the builder's own PRs that ask for changes go out by rule: there a click only delayed the fix, and 46 of 105 drafts on the builder's PRs went stale while they waited. The builder can push and open PRs, but never approve, merge or post a review.

Cheap checks before expensive ones

The second review starts only once CI passes and the CI reviewer holds nothing above low open. Low findings are left to the review to weigh: when they sent PRs back too, 38 of 111 rounds went back for lows alone. From the second round on, the review reads only what changed since its last posted review, plus the high-risk paths in full.

Auto-merge as policy, not as trust

The merge rules live in their own repository with their own GitHub App, versioned and reviewed like code, and one repository variable turns them off. Hard rules (protected paths, open findings, recent reverts) cannot be overridden from the dashboard; soft ones (size, labels) can, by a person, one PR at a time.

Waiting lists are worked out, not accumulated

Needs you began as a list of events, each closed only by the step that handled it, and 26 of 42 waiting items had gone out of date. It is now computed from where every PR stands: what will never need a person is closed with the reason, what waits on something else is held with one line saying what, and the rest is the list.

One codebase for any repository

Everything particular to a project moved into one project file: repository, board, column names, install steps, review rules. The refactor was proven safe by loading the production configuration before and after, identical down to every rendered prompt, byte for byte. init sets up a new repository and board in one command.

Security

The agent's container holds no credentials

Each agent run, install script and git command that touches a workspace runs in a throwaway container. Everything worth stealing stays on the host side of this line.

Host
  • GitHub token
  • Model API key
  • Read-only mirror of the repository
  • API proxy: issues a token per run
  • Imports the run's commits, checks every object, pushes
mirror ⟶ originThe workspace can fetch, never push.
⟵ git bundle on stdoutTo push, the container hands over a bundle. Host git never runs inside a workspace, because it would obey the agent's .git/config.
⟵ run token ⟶ model APIValid for this run and the model endpoints only; revoked when the run ends.
✕ private addressesThe host, the local network, other containers and cloud metadata are rejected.
Container
  • The agent and its workspace
  • Firewall set up as root, then root and every capability dropped for good
  • No token, no key, no route to the host

Each control is tested against real Docker with a control case: the attack is shown to work without the sandbox, then to fail with it. Fourteen such end-to-end tests run alongside more than 440 unit tests. The sandbox is the mode for new projects; the first team's own machine ran without it.

What went wrong

And what changed because of it

PRs vanished from the merge queue

GitHub records the removal only on the PR's timeline, so nobody noticed.

The workflow reads it, retries once when the runner or the clock failed it, and otherwise sends it back to the builder with the failing step and its errors. The first card caught a PR that had silently failed twice.

A daily spending limit that was not daily

It counted from process start, reset on restart, and each daemon counted alone.

It now sums the day's runs from the shared run ledger.

A reviewer that would wait forever

On a new project it waited for a CI reviewer only the first team ran.

Found by running a brand-new repository end to end. The CI reviewer is now optional.

A path check the proxy could be talked out of

/v1/messages/../files passed the allow-list and was normalised into something else on the way out.

Caught in self-review. The check now runs on the path as it will be sent.

Open the review

Redrawn from the dashboard with the demo repository's ticket. In the live tool the reason is written in the owner's language.

The next layer takes decisions off the person's list. A model reads each item that waits on them and writes down what it would do, how sure it is and why. It acts on none of it yet. Its calls are set against what the person then did, by kind of decision, and a kind is handed over only once the two agree.

By rulePost a review the way the rule says, acknowledge a notice.
JudgedAnswer the builder's question, send a pass to auto-merge.
A person'sApproving a teammate's PR, or merging past a review that asked for a person. These stay gates whatever the score.

Items a rule closed before the person decided are left out of the agreement rate, so it measures only real decisions. A call that keeps failing is tried three times and then left alone.

What is next

Still open

  • Hand over the first kinds of decisions the manager agrees on.
  • A GitHub App identity for the builder, so its PRs and a person's approvals come from different accounts.
  • A full model run inside the sandbox with an API key. So far it is verified up to the agent starting and reaching the model through the proxy.
  • An egress allow-list, so code in a run cannot send what it reads to arbitrary public addresses.
