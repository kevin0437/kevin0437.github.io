An automated workflow from GitHub ticket to merged pull request

Claude agents take labelled tickets from a project board, write the code, open and review pull requests, and a policy merges what passes. People see one page: only what needs them.

My part

Designed, built and ran it end to end: architecture, agent prompts, GitHub integration, the sandbox, the dashboard, and the day-to-day calls on what the agents may do alone.

Problem

A product team had more well-specified tickets than people, and code review was already the bottleneck.

  2. AgentBuild

  3. RuleCI and CI reviewer

Median builder run 27 min, review 12 min, PR opened to merged 21 hours. The builder asked a person 25 questions instead of guessing. From the run ledger and the GitHub API, 29 October to 10 November 2026; costs are SDK estimates at API prices, and the team ran on a subscription.

A person decides what goes out on other people's work

A review of a teammate's PR is a draft until a person posts it. Only reviews of the builder's own PRs that ask for changes go out by rule: a click there only delayed the fix, and 46 of 105 drafts on its PRs went stale waiting. The builder can push and open PRs, never approve, merge or post a review.

Cheap checks before expensive ones

The second review starts only once CI passes and nothing above low is open. Low findings are left for the review to weigh: when they sent PRs back too, 38 of 111 rounds went back for lows alone. Later rounds read only what changed since the last posted review.

Auto-merge as policy, not as trust

The merge rules live in their own repository with their own GitHub App, versioned and reviewed like code. Hard rules cannot be overridden from the dashboard; soft ones can, by a person, one PR at a time.

Waiting lists are worked out, not accumulated

Needs you began as a list of events, and 26 of 42 waiting items had gone out of date. It is now computed from where every PR stands: what will never need a person is closed with the reason, the rest is the list.

One codebase for any repository

Everything particular to a project moved into one file. The refactor was proven safe by loading the production configuration before and after: identical, down to every rendered prompt. init sets up a new repository and board in one command.

What went wrong, and what changed

PRs vanished from the merge queue

GitHub records it only on the PR's timeline.

The workflow reads it, retries once when the runner failed, and otherwise sends the PR back with the failing step. The first catch had silently failed twice.

A daily limit that was not daily

It reset on restart, and each daemon counted alone.

It now sums the day's runs from the shared ledger.

A reviewer that would wait forever

For a CI reviewer only the first team ran.

Found by running a brand-new repository end to end; the CI reviewer is now optional.

A path check the proxy could be talked out of

/v1/messages/../files passed the allow-list.

Caught in self-review; the check now runs on the path as it will be sent.

Security

The agent's container holds no credentials

Each agent run, install script and git command that touches a workspace runs in a throwaway container. Everything worth stealing stays on the host.

Host
  • GitHub token
  • Model API key
  • Read-only mirror of the repository
  • API proxy, one token per run
  • Imports the run's commits, checks every object, pushes
mirror ⟶ originThe workspace can fetch, never push.
⟵ git bundle on stdoutHost git never runs inside a workspace; it would obey the agent's .git/config.
⟵ run token ⟶ model APIValid for this run and the model endpoints only.
✕ private addressesHost, local network, other containers and cloud metadata are rejected.
Container
  • The agent and its workspace
  • Firewall set as root, then root and every capability dropped
  • No token, no key, no route to the host

Each control is tested against real Docker with a control case: the attack works without the sandbox and fails with it. Fourteen such tests run alongside more than 440 unit tests. The sandbox is the mode for new projects; the first team's own machine ran without it.

A clinic workflow platform I built end to end, with an AI assistant at its centre

Patient charts, procedures, scheduling, documents and faxes, tasks, stock and staff for clinics across several sites, in one system built for many organisations. On every page an assistant looks things up and gets things done through the same API and permissions as the person asking, and changes nothing without their click.

194data models
~480assistant tools

My part

Designed and built all of it on my own: the product, data model, API, web app, AI features, the assistant, CI and releases. About 550,000 lines of TypeScript and 300,000 more of tests, March to November 2026.

Problem

Staff ran patients, procedures, faxes, schedules and stock across disconnected tools and paper, and spent hours reading documents to file them. The practice needed one system, and AI to do the reading, where a wrong patient match or a silent change to a record is never acceptable.

The product

One system for the clinic's whole day

More than 120 routes in a dense, keyboard-first web app that turns into a phone layout below 768 px.

Record a visit; get a transcript with speakers, notes in the clinic's templates, a live checklist and follow-up fields filled in.

The AI assistant

An assistant that acts as the user, and never more

Staff ask in plain words: pull up her latest imaging report, list my open tasks and each patient's open orders, book a follow-up. It answers with links into the app, opens pages with forms already filled in, reads files dropped into the chat, and keeps going after the tab is closed.

  1. PersonAsk

    The message becomes a run in a job pool: one run per conversation, followed live by any page that opens it.

  2. RulePick the tools

    12 core tools, plus 12 of about 480 found by keyword and embedding search fused by rank; the long tail is one search away. A tool the user's role cannot use is never offered.

  3. AgentPlan and look up

    A checklist for a request of several steps. Reads in a round run together; writes run one at a time, in order.

  4. RuleCall the API as the user

    Every tool goes back through the API with the user's own credentials, so permissions, tenant and audit are the real ones. A result over 8,000 characters is kept whole and read in parts.

  5. RuleTreat results as data

    Every result goes back marked as data, not instructions. Text that reads like an instruction is cautioned and logged, never dropped.

  6. PersonConfirm the write

    A write becomes a card naming what it changes, with fields to edit. Single-use, the user's own, gone after ten minutes; a second click gets the first result back.

  7. RecordSummarise the run

    How it ended, rounds, tool calls, cost and the build that served it: ids and counts, never content.

Agent Rule Person LangChain's createAgent on Amazon Bedrock's Converse API, with Claude models.

Tools made from the API's own schemas

Some tools are hand-written; most were generated from an audit of the API's endpoints. A write tool takes its parameters from the same Zod schema its endpoint validates with, so the two cannot drift. An organisation can switch a tool off or add its own phrasing for retrieval, never rewrite one: names and descriptions stay in code, reviewed and measured.

My own confirmation cards, not the framework's

LangChain's human-in-the-loop middleware failed my proof of concept: it held reads back until approval, dropped an approved write when another was rejected, and ran a write twice on a double click. Writes became stored, single-use cards that any server process can confirm.

Writes need a click; reads need a guard

With every write behind a click, the exposed surface is what the model reads: faxes, documents and form answers can carry text aimed at it. The guard observes and cautions and never blocks, because a clinical note that happens to look like an instruction must still reach the model; silently dropping data is the worse failure.

Assistant internals

Built to run unattended, and measured before it changes

Turns that survive a crash

Every tool call is checkpointed in Postgres, and the process running a turn holds a short lease it keeps renewing. When a process dies, another takes the turn over with a compare-and-swap and re-runs only the call that was in flight.

At most one process ever continues a turn.

Bounded, always

300 seconds a turn, 30 to the first token, 15 between tokens, 20 for a read. A write is never aborted half way. At the round cap the model gets one more call to answer from what it found.

Stop works exactly the way a limit does.

Retrieval tuned on data

Keyword ranking at half weight: equal weight dropped the tuning score from 62/64 to 56/64. One vector per usage example: averaging buried an exact match at rank 25 of 406. Earlier messages at half weight took follow-ups from 9/14 to 12/14.

The core set is every tool used in at least 2% of turns.

Cached by design

Bedrock caches tools before the system prompt, so I split the prompt into a shared and a per-user half, put a cache point after the fixed tool head, and moved rules a tool needs onto that tool.

Cost per round down 35% on a new subject, 69% on the same one.

Context that stays small

History is budgeted at 8,000 tokens, after measuring 76 real sessions. Past 40,000 tokens in a turn, older tool results are cleared from what the model is sent. Long conversations are summarised in the background; a recall tool reads back what was cut.

A summary holds patient data: stored on the tenant's row only.

Memory without a pending queue

"Remember…" saves a preference at once. A small model proposes the implicit ones, kept above 0.85 confidence, and a nightly job merges similar rules and archives idle ones.

Each user sees and edits their own.

The task-completion eval runs whole conversations with the real engine, model and tools, and never confirms a card. Answers are judged by text checks, and where a fact can be laid out many ways, by a model judge calibrated on answers whose verdict is known. Single runs are noisy, and I read them that way.

AI in the product

AI does the reading; rules and people decide what it may change

Intake that files itself, carefully

Merged PDFs are split, each page read from its own text, else by OCR, else by a vision model, and the person it is about matched. A document files itself only on agreeing identifiers with no contradiction, and only when an independent model check agrees; anything else waits in a review queue with ranked candidates.

Any error in the check counts as "do not file".

Documents read in full, searched by passage

Long documents are read in 30-page sections, then combined. Passages are embedded with a model-written context, ranked three ways, fused by rank and reranked by a cross-encoder. Every passage is re-checked against the caller's live access.

A slow reranker falls back to the fused order.

Imaging studies matched like a person would

Code narrows the candidates to the same birth date and a name rule; a model judges each pair same, different or unsure. A study links only when it has exactly one "same", and every link can be undone.

"A missed study is acceptable and a wrong one is not."

A visit, recorded into notes

A recording becomes a transcript with speakers and notes in the clinic's templates. An autofill under 90% confidence, or over a filled field, is only a suggestion, and the AI's first draft is kept as version 0.

Quotes must appear word for word in the source.

Memory that cannot drift

Each clinician's preferences are learned from their edits. A rewritten rule must keep the original wording, pass a second model's drift check, and can be reverted in one click; template changes are only ever proposed.

Examples taken from edits are redacted first.

One model setup for every purpose

Each organisation picks a model for each of 11 purposes, all on Bedrock's Converse API. Every call writes a usage row with its cost, and every AI feature ships behind a flag with a kill switch.

15 eval suites run the real prompts on the real models.

Evals with safety gates, not just scores

A case passes on a majority of repeated attempts, and one false accept or one wrong patient fails the whole run. That is how a candidate model that scored 18/20 on the filing check, with two false accepts, was turned down; the model in use scored 20/20 with none.

Data and tenancy

A schema per organisation, isolation proven on a real database

Each organisation gets its own PostgreSQL schema, cloned from a template with structure only, and its own FHIR project. The organisation comes from a header checked against the user's memberships, never trusted from the token, and a missing FHIR credential fails closed. Most tests mock the database, so a test on real Postgres proves the isolation.

FHIR where it is the standard, Postgres where the clinic works

Identity, appointments and questionnaires live in FHIR; procedure tracks, insurance and tasks in Postgres. A patient is written locally first and synced by a worker with an idempotent create, so registration works while FHIR is down, and a FHIR read times out at five seconds and falls back.

Migrations that never stop the app

Changes are additive, because old and new code run side by side during a rolling reload. CI replays the whole migration history into a throwaway database and diffs it against the schema, and the authoring script refuses a DROP.

Stock as lines, with a ledger

An item's stock is a set of lines, each a place, a lot and an expiry, and the item's total is their sum, written in the same transaction under a lock. Every change names its line in a ledger, and a transfer between sites is in transit until it is received or cancelled, once.

Security and audit

Authorization nobody can forget

Permissions are resource-and-action pairs per organisation, and every denial is audited. A test fails the build if a router is added without authentication; each public one carries a written reason.

An audit log that shows tampering

Writes and reads of patient data are captured automatically. Each row carries an HMAC and cannot be updated, each day is sealed with a digest, and the log exports as FHIR AuditEvent and OCSF. An assistant run's id is the trace id that ties its audit rows to its logs.

Patient data stays out of queues and logs

Queue messages carry ids only, enforced in code, and logs are redacted. A signed form is sealed with a SHA-256 hash of the exact text and an HMAC. A fax is never retried blindly: a duplicate fax is a duplicate disclosure.

Frontend

An Excel-like table, built for density

DenseTable is a CSS Grid with fixed pixel columns, so resizing one never moves another; 22 or 24 px rows; Excel-style keyboard movement between cells; sorting and filtering on the server, with the same matching rules in the browser; and a failed load is never shown as an empty list.

One list of columns, a table or cards

A sheet is one list of columns, drawn as a table on a wide screen and as labelled cards on a phone, so the two cannot drift. One Field component draws every input: the page sets its size, text is 16 px on touch so iOS does not zoom, and dates follow the clinic's time zone, not the device's.

Work that survives the browser

Uploads go straight to S3 in 5 MB parts, four at a time, and carry on while the user moves around the app. A visit recording is saved to IndexedDB every second and sent at the next start if it never finished. A stale save is refused with the server's copy, never written over another tab's.

984 test files and over 15,000 tests (Vitest and Testing Library, 22 suites against a real Postgres), a headless check that every field's text lines up within half a pixel at desktop and phone widths, and 8 CI workflows. Releases are rolling reloads with no downtime.

In progress

Next: the final stages of the assistant's v2 design

A redesign against how current coding and research agents work, checked against the code line by line. Its first stages, a conversation as one append-only thread with its prompt frozen at the start, are ticketed and under way. These are the last three.

A tool list that never changes

Stage C · tool delivery

A fixed head of core tools and a directory naming about 255 common actions. Full definitions arrive by retrieval or by exact name, and every call goes through one dispatcher that checks the tool, the user's permission and the arguments. The prompt cache then holds for the whole conversation.

Plans, approvals and steering

Stage D · interaction and control

A batch of writes is proposed as a plan and approved on one card, in full or in part; a write that leaves the plan needs approval again. Three cards refused or expired in a row stop the run to ask. The page shows each step as it runs, and a message sent mid-run is taken in after the current round instead of being refused.

Sub-agents and a checker

Stage E · delegation

A task tool starts sub-agents on child threads, inside the turn or in the background job pool, in parallel under a cap and a budget: research, data analysis, document review. Read-only by default, each returns a structured report with its sources. A long result can go to an independent checker that grades it against a rubric and sends it back for rework.

Code execution for work at scale

Stage E · deep mode

For work over many records, the model writes a short script that loops over read-only tools and sub-agents and returns only the result: check 200 follow-ups, summarise them by provider. It runs in a sandboxed interpreter in a worker process; writes stay outside the script, on cards.

A personal workspace

Stage E · memory

One folder for the model: its own notes in Postgres, the user's files in S3, and search over their past conversations, isolated by organisation and user. It keeps record ids, never copies, so every read is permission-checked again.
